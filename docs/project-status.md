# 项目状态

更新时间：2026-07-23

## 当前阶段

低保真原型已完成第一版，进入产品评审与目标用户验证。产品负责人已确认 App 功能、信息架构、核心流程、MVP 范围和推荐的开放决策方案，尚未开始正式业务代码实现。

## 已形成的共识

- 产品定位为家庭餐食决策与厨房库存系统，Agent 是入口而不是唯一界面。
- 首要风险是库存维护成本，而不是模型生成能力。
- 库存必须按批次和事件管理。
- 过敏、日期、权限与食品安全使用确定性校验。
- 首发应验证完整闭环，不同时建设四套独立原生客户端。
- 一级入口采用“今天、库存、采购、家庭”，Agent 作为上下文入口而非独立 Tab。
- P0 采用手动搜索、最近项、常用模板和文本录入；语音、条码及 OCR 放入 P1。
- 菜单按单道主食或 1–3 道菜的一餐组织。
- 菜单选择采用“建议数量 + 预选组合 + 可选菜增减”，不再使用三个完整菜单三选一。
- MVP 使用所有者、普通成员和无登录用餐档案三类身份。
- P0 只做应用内临期提醒，外部通知放入 P1。
- 微信小程序作为首发目标，架构保留 Android、iOS 和 HarmonyOS 扩展能力。

## 已确认的产品决策

产品层选择统一记录在 `docs/product/open-decisions.md`，已作为原型基线确认。原型阶段重点验证：

1. 首次录入能否在较低维护成本下完成。
2. 用户能否理解建议菜品数量，并高效增减可选菜组成一餐。
3. 采购完成后的入库确认是否足够轻量。
4. 做饭完成后的库存扣减和剩菜回库是否容易理解。

跨端框架、后端运行时、登录体系、部署环境以及正式数据来源仍需在原型验证后通过技术 ADR 确认。

## 本阶段完成

- 在 `docs/design/low-fidelity-prototype.md` 记录 16 个原型页面、验证目标、待验证阈值和建议评审任务。
- 完成可点击低保真原型，覆盖首次引导、首批食材、今天吃什么、建议组合与可选菜、本餐确认、共享采购、买后入库、做饭模式、完成状态、库存扣减和剩菜回库。
- 桌面评审视图提供页面目录、当前风险和验证问题；窄屏视图按微信小程序优先场景展示。
- 原型明确区分“未知/没有”“已买/已入库”“做完/已确认扣减”，并提供库存并发变化后的重算演示。
- 已按完整闭环走查，并验证 5 项模糊数量录入、建议组合增减、整餐汇总、共享勾选、部分完成、用量调整、批次排除、冲突重算和剩菜回库。

## 建议的下一里程碑

按 `docs/design/low-fidelity-prototype.md` 中的五个任务开展可用性评审，记录完成时间、误触、求助和口头理解。优先决定：

1. 首次录入是否需要进一步压缩步骤或默认项。
2. 建议数量、预选组合和可选菜增减是否足够支持 20 秒内决策。
3. “已买待入库”是否可以批量确认且不会造成状态误解。
4. 餐后扣减是否需要进一步合并完成状态、消耗确认和剩菜回库。

原型验证后再更新对应产品决策，并进入跨端技术栈 ADR 和开发。
