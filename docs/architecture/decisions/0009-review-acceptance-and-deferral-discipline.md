# ADR-0009：设计门禁的停止谓词与延迟项纪律

- 状态：Accepted
- Accepted 日期：2026-09-12
- 日期：2026-09-12
- 负责人：产品负责人、设计门禁总控、独立审计与质量
- 上位决策：[ADR-0007：食品知识治理与确定性领域核心](0007-food-knowledge-governance-and-domain-core.md)
- 规划：[阶段 09P：安全知识治理与确定性产品核心闭环](../../plans/2026-08-stage-09p-safe-deterministic-product-core.md)

本 ADR 的修订方向已由产品负责人明确批准：09P 设计准备阶段反复出现无界复审轮次，
需要把停止谓词与延迟项登记固化为仓库内**可机器核验**的规则，并把修订回读与里程碑级
轮次上限固化为仓库内的门禁规则（后者由收口记录逐轮登记，不以脚本自证）。本 ADR 只
收敛「何时可以停止一轮设计审查、以及未被本轮修复的发现如何登记」，不改变任何安全
判据，也不授权实现、合同冻结、migration、DB/RLS、API/client、外部能力或任何里程碑状态。

## 背景

09P 的设计准备材料（decision pack、evidence、shadow design）使用三条互相盲评的
lens（fail-closed / authority / adversarial）独立复审。这一实践抓到过真实缺陷，必须
保留。但它的停止谓词是无界的：一轮被判定可以停止，仅当「复审者本轮剩余的发现计数
为零」，而这个计数会被复审过程本身持续再生产。已核验的结构性缺陷有三条。

第一，停止谓词等于复审者的残余计数。修一处、再复审、又出现新发现，没有任何
「本轮必须闭合、否则升级」的界线。

第二，修订协议只修被点名的那一处，不回读同一文档中持同一主张的其他句子。于是每次
修复都会制造下一轮的发现。可核验的实例：WP-O3 的 §4.2 在 r1/r2/r3 被反复改写；
WP-O4 的 §4.1.1 表格在 r2/r3/r4/r5 被反复改写；WP-O4 的残余 P2 计数随轮次为
11 → 6 → 7 → 6 → 2，非单调，直到 r5 才收敛。WP-O4 的评审谱系本身已记录
「每一轮只改被点名处、未回读持同一主张的相邻句」是多数残余的来源。

第三，没有里程碑级轮次上限。仓库里唯一存在的 2 轮上限位于未版本化的 `.local/` 过程
文件中，且每份 remediation 计划按任务重置它。后果可核验：M5 累积了 17 份计划文档、
12 轮以上；M1 在 599 份审计报告中有 460 份属于它；M2 已在 gap-gate 第 10 节被拆成
六个剩余阶段，若按阶段重置轮次上限，将意味着十二轮。另有两条结局说明无界轮次并不
总是以收敛告终：D0 设计线（D0-R1/R2 双 BLOCK 后，D0-R3 复审从未创建）与 G2-r10
协议（r1—r10，终态 `PROPOSAL_BLOCKED`，仅存在于 `.local/`）都在未闭合的情况下静默
弃线。

**必须诚实记录的反事实。** 0/0/0 的实践抓到过真实的 fail-open 缺陷，其中数条被标为
P2。典型是 R2-ADV-03：`identityPolicyVersion` 是 identity key 的成员，版本变更会移动
namespace，于是旧的 non-reuse landmark 不再覆盖（攻击面 (d) 的变体）；该缺陷被评 P2，
仅因 P2 计作阻断才被修复。因此本 ADR 不得削弱设计门禁对语义缺陷的阻断能力，也不得
全局下调 P2。

产品负责人已明确批准本 ADR 的修订方向。本 ADR 不代替产品负责人对第 8 条所列仍开放
事项的裁定。

## 决定

### 1. 设计门禁与实施审计各自适用不同的判据集

仓库不再对所有环节套用同一条严重度规则，而按「是否授予实施权威」区分两条轨道。

- **设计门禁（design gate）**：适用于设计准备产物——decision pack、evidence 文档、
  shadow design，以及一切不授予实施权威、不冻结合同的材料。任一条语义缺陷即阻断。
  对任何语义主张的改动，继续使用三条互相盲评的 lens（fail-closed / authority /
  adversarial）。
- **实施审计轨道（implementation audit track）**：适用于对代码、migration、gate 的
  动态审计。既有规则不变——只有被确证的 runtime 缺陷或凭据泄漏阻断；其余发现记为
  P2，由总控裁定。

### 2. 停止谓词改为「残余 P2 全部本轮修复或登记」，不再等于复审者残余计数

一轮设计门禁可以停止，当且仅当：`P0 = 0` 且 `P1 = 0`，且每一条残余 P2 要么
**本轮修复（FIXED THIS ROUND）**，要么**已登记入延迟项登记表
（ENTERED INTO THE DEFERRAL REGISTER）**。停止谓词是这三个合取条件，不是
「复审者说剩余发现为零」。

**「本轮修复」不是自证。** 被声明为 FIXED THIS ROUND 的修复，须在同一轮判停之前由
一条**独立于修复者**的 lens 对修订后的文本做一次确认性回读（confirmatory read），
该确认性回读须覆盖这批修复所改动的每一处；未经该回读确认的修复不得计入停止谓词。
换言之，最后一批修复不能被它自己当作「最后一眼」。历史证明 r2/r3/r4 的多数残余恰
来自「只改被点名处、未回读持同一主张的相邻句」的未复核修复（见 §背景第二条、
`docs/evidence/stage-09p-m2/wp-o4-review-history-r0-r4.md`）。

### 3. 延迟准入按内容判定，不按 P 标签

一条**已知缺陷（finding）**只有在「其修复不触碰任何规范性内容、且不改变任何规范性
主张」时才允许登记延迟——即它纯粹是记账：行号、字节/行计数、表头，以及**出处/交叉
引用更正**。出处/交叉引用更正是否算记账，判据是**误导**，不是「改正后的引用是否承载
所主张的内容」：一条更正算记账，**当且仅当**循着有缺陷的引用所得出的必需行为，与循着
改正后的引用所得出的必需行为**完全一致**。若错误引用会把读者引向**另一条**规范规则
——读者循缺陷引用会推出不同的必需行为——该缺陷即**误导**读者，属语义修复，
**必须本轮修复**（历史实例：WP-O3 §15 的 AUTH-P2-01——把 `WP-O1 §6.2(3)` 改为
`§6.2(1)`，表面是交叉引用，改正后的 §6.2(1) 确实承载所主张的 fail-closed 规则
「能完整证明从未越过 handoff 才维持 `N`」，但原引用的 §6.2(3) 恰是**相反**分支
（重启/身份重绑/记录缺失 → 进 `U`），读者循缺陷引用会推出相反的必需行为，故该缺陷
误导读者，属语义修复而非记账）。

**任何**修复会触碰规范性句子的发现——凡涉及 must / shall / only / never、invariant、
fail-closed、identity、namespace、authority、key、binding、entitlement 的任何一处——
**无论其 P 标签为何，都必须本轮修复**。本条的用途正是防止一个被误标为 P2 的语义缺陷
（即 R2-ADV-03 一类）滑过门禁。

**三项内容准入类别（`admissionBasis`）。** 允许在登记表存在的条目，按其**内容类别**
分三种，与 P 标签无关，且每笔必须显式声明其中一种：

1. `bookkeeping`——纯记账：行号、字节/行计数、表头，以及上段定义的**不误导读者**的
   出处/交叉引用更正。
2. `open-design-question`——一个**仍未关闭的设计问题**：其解决是尚待作出的设计决定，
   而非一处已知缺陷（例如 Q10 的版本边界机制）。
3. `evidence-obligation`——一处**语义修复已在本轮落地**的命名义务，其闭合只差**真实
   证据**（例如 O9-5/G8 的 non-reuse 义务：规范义务已写入决策包，缺的是 W37 动态证据）。
   以本类别登记**不**等于该发现被解决——该义务在证据取得并解除前**保持 admission
   blocker**，故每条 `evidence-obligation` 条目的 `closeTrigger` **必须写明
   `admission blocker` 这一措辞**，由 checker 机械核验（`closesAtModule` 只取闭合模块
   闭集内的模块标识，不承载该措辞）。

**硬边界（不得绕过）。** 该三类别**不得**用来递延一处**已知的、未修复的**语义缺陷：
任何已知缺陷只要其修复会触碰规范性内容，就必须本轮修复，与 `admissionBasis` 无关。
因此 `evidence-obligation` 只适用于「修复已落地、仅余证据」的义务，`open-design-question`
只适用于「设计决定尚未作出」，两者都不能把「发现」与「尚未取得的证据」之间的边界
当作降低阻断级别的通道。

### 4. 里程碑级轮次上限，写入仓库、按里程碑身份固定

每条设计线设一个**按里程碑**计数的轮次上限：**同一设计线在同一里程碑内至多 3 轮
门禁**（初始盲评 1 轮 + 回读修订至多 2 轮）。该上限的**数值写于本 ADR 与计划
§12.3**，属版本化、可评审的仓库规则——不再位于未版本化的 `.local/` 过程文件里。

- **按里程碑身份计数，永不按任务、按阶段或按子里程碑重置。** 里程碑身份即计划固定的
  M0—M6 顶层集合；把一个里程碑再拆成阶段或子里程碑（例如把 M2 拆成 M2a…M2f）**不产生
  新的计数起点**，也**不得**以重新命名、增补顶层里程碑或任何同义手段，为一条在飞的设计
  线取得新的计数起点。按这种拆分重置计数，正是本条点名的反模式（M2 已在 gap-gate 第 10
  节被拆成六个剩余阶段，按阶段重置即等于十二轮）。
- **逐轮登记，达到上限即升级。** 每条设计线的每一轮门禁，其**轮次序号**必须在该门禁
  的收口记录中显式登记；达到上限时要求的动作是**携带未闭合发现升级至产品负责人**，
  绝不静默弃线；D0 与 M5 的结局是这两条路径的对照。
- **到达上限不构成接受。** 到达上限、以及产品负责人在上限处的裁定，**都不构成接受**，
  也**不**把任何未闭合的、属 §3 内容判据的规范性发现移出阻断态。上限只改变「由谁裁定
  下一步」，不改变「发现是否闭合」。

### 5. 修订后强制回读所有持同一主张的句子，且修复本身经独立确认

一次修订必须在每一处编辑之后，回读并对齐全文所有持同一主张的句子——不只是发现所
点名的那一句。这是门禁判据，不是期望。复核者可通过「对同一主张做全文检索、逐句
比对」来核验：若同一主张在一处已改、在另一处未改，本轮不得判为闭合。

回读覆盖的是「同一主张的兄弟句」；它**不**覆盖修复本身新引入的缺陷。后者由 §2 的
确认性回读负责：本轮修复所改动的每一处，须由一条独立于修复者的 lens 在判停之前
重新读一遍，而不是留给下一轮。

### 6. 延迟项登记表与字段

建立一份机器可读的登记表，登记每一条被允许延迟的条目。登记表遵循仓库既有登记惯例：
严格标准 JSON（首键 `schemaVersion: 1`，不允许注释），由 `.mjs` checker 机械核验，
对不可读、schemaVersion 不为 1、缺字段、多字段、**重复成员**一律 fail closed。每条登记项
**必须有且只能有**主键 `id` 及下列**六个**字段：

| 字段 | 含义 |
| --- | --- |
| `owner` | 具名责任主体：一个具名**个人**，或 **M2 gap-gate §4「统一 gap inventory：粒度、去重与 owner」**定义的责任**角色**——二者都是「具名可问责方」。确实无人负责时写显式哨兵 `unassigned:<非空理由>`，由 checker 计数并逐条上报（裸 `unassigned` 或空理由判非法） |
| `closesAtModule` | 闭合的模块或外部方（关闭该义务的交付物） |
| `evidenceNeeded` | 关闭前必须取得的真实证据 |
| `closeTrigger` | 触发关闭或再评审的事件 |
| `expiry` | 到期时间；无到期者按 §6.1 的哨兵写法 |
| `admissionBasis` | 内容准入类别：`bookkeeping` / `open-design-question` / `evidence-obligation`（§3） |

字段名一律 camelCase，与登记表本体及 checker 的键名一致（不使用连字符键名）。

`owner` 的未指派哨兵与 `expiry` 的 §6.1 同形：`unassigned:<非空理由>` 由 checker 计数
并逐条上报；裸 `unassigned` 与空理由（`unassigned:` 后无理由）一律判
`OWNER_UNASSIGNED_MALFORMED`。具名个人与 **M2 gap-gate §4** 定义的责任角色均为合法
`owner`——本仓库当前不存在具名个人，故实际取值是责任角色或该哨兵；该节自身亦明定
「最终指派必须由总控完成」，故未指派时使用哨兵而不得留空。

#### 6.1 expiry 与 `unassigned` 哨兵

`expiry` 只有两种合法取值：

1. 完整 ISO 8601 **带时区偏移**的时间戳——沿用
   [`security/audit-exceptions.json`](../../../security/audit-exceptions.json) 的口径
   （例如 `2026-11-08T23:59:59+08:00`），到达到期时间而未取得显式决议即 fail，禁止静默续期；
2. 哨兵 `unassigned:<理由>`——**必须**紧随一个非空理由（例如
   `unassigned:Q10 未关闭前保持 admission blocker`）。**裸 `unassigned`（无理由）不合法，
   一律判 `EXPIRY_MALFORMED`。**

**登记不等于闭合。** 登记表记录的是「有界等待」，不是「已关闭」。`unassigned:<理由>` 是
**有界**等待而非无限期停放：登记表顶层以 `reviewByMilestone` 声明下一个里程碑收口
（当前为 `M2`），每条 `unassigned:<理由>` 条目**不得跨过该收口**——到达该收口时，每条
必须**逐条转为真实日期或明确关闭**，否则该收口不得判为通过。

### 7. 本 ADR 明确不改变的控制

- 设计门禁对语义 P0/P1 **以及 §3 内容判据下的语义 P2** 的阻断能力；
- 对语义改动的三 lens 复审；
- 计划 §12.1 的 A/B 双审计清单：active 食品安全/allergen 数据、hard-constraint 引擎、
  migration/RLS、Recommendation 安全快照、Meal completion 与 leftover 事务（以及
  M6 最终候选）；
- 运行与审计的分离，以及「被平台中断且没有正式报告的会话记为 INVALID，而非 BLOCK
  或 CLEAN」的规则；
- 实施者只能报告 `Implemented`、永不自接受（`Accepted`）的规则。

**到达轮次上限不构成接受**，也**不**把任何未闭合的、属 §3 内容判据的规范性发现移出
阻断态（见 §4）；上限只决定由谁裁定下一步，不改变发现是否闭合。

### 8. 仍属产品负责人决定、本 ADR 不予裁定的事项

本 ADR 不裁定以下两项，它们继续保持为产品负责人的决定：

1. 是否正式退役 G2-r10 协议，并以替代的可复现性协议取代它；
2. 是否在 `M1_LIMITED` 下授权一个有界的合成纵切（synthetic vertical slice）。

## 不采用的方案

- 不采用「复审者剩余发现为零」作为停止条件；它把停止谓词交给会被过程再生产的量。
- 不采用按任务、按阶段或按子里程碑重置的轮次上限；它把上限变成每次都重新开始的形式。
- 不对到达轮次上限的线静默弃线（D0 与 G2-r10 的结局），而是升级至产品负责人。
- 不把延迟准入建立在 P 标签上；标签可被误用，内容不可。
- 不把「登记」当作「闭合」，不允许裸 `unassigned`（无理由）的登记项，也不允许
  `unassigned:<理由>` 条目跨过 `reviewByMilestone` 收口仍不转期或关闭。
- 不把「到达轮次上限」当作接受，也不借此把未闭合的 §3 规范性发现移出阻断态。
- 不全局下调 P2，也不削弱设计门禁对语义缺陷的阻断。

## 影响

- 设计门禁的停止成为可判定的：残余 P2 非修复即登记，没有第三种状态。
- 修订成本上升（必须回读同一主张的全部句子），但每轮制造的下一轮发现减少；WP-O4 的
  11 → 6 → 7 → 6 → 2 一类非单调计数应被收敛。
- 里程碑级上限把「无限复审」转化为「到达上限即升级」，代价是需要产品负责人在上限处
  裁定剩余发现；但到达上限与产品负责人的裁定均**不构成接受**，未闭合的 §3 规范性
  发现仍在阻断态。
- 被登记的延迟项成为可审计的**有界**等待清单：每笔带内容准入类别（`admissionBasis`）
  与到期口径，`unassigned:<理由>` 项带非空理由且不得跨过 `reviewByMilestone` 收口，
  而不是被遗忘或被静默抹平的发现。
- 本 ADR 不授权任何实现、合同冻结、migration、DB/RLS、API/client、外部能力或里程碑
  状态变化。

## 验证与接受边界

- 登记表由 `.mjs` checker 机械核验：`schemaVersion` 必须为 1；缺字段、多字段、重复
  成员、非法 `expiry`（含裸 `unassigned`）、非法 `owner` 哨兵（裸 `unassigned` 或空理由）、
  `evidence-obligation` 的 `closeTrigger` 未写明 `admission blocker`、未知
  `admissionBasis` 一律判红并 fail closed；checker 通过固定的 PASS/FAIL 输出与 exit code
  报告，不回声不可信输入。
  重复成员由 checker 对登记表原文做一次键扫描检测，且键按**解码后的值**比较：`JSON.parse`
  会静默折叠重复键，而同一键的两种转义写法（unicode 转义与字面量）解码后相等、属同一键，
  故既不能只依赖解析结果，也不能只比原文键字面量。
- 停止谓词（`P0 = 0` ∧ `P1 = 0` ∧ 每条残余 P2 非修复即登记）与延迟准入（按内容、不按
  P 标签，并逐笔声明 `admissionBasis`）在每份设计门禁的收口记录中显式判定。
- 轮次上限为 **3**（数值写于本 ADR 与计划 §12.3），按里程碑身份（M0—M6）计数，不按
  任务/阶段/子里程碑重置；每轮序号在收口记录中逐轮登记。本 ADR **不声称**存在自动
  计数脚本：计数以收口记录中的逐轮登记为准，由独立复审者与总控核验；不得以「无脚本」
  为由跳过上限或推迟升级。
- 本 ADR 与 [`security/audit-exceptions.json`](../../../security/audit-exceptions.json)
  的到期模型一致：带真实到期者用完整 ISO 8601 带时区偏移（该文件为
  `2026-11-08T23:59:59+08:00`），且禁止静默续期——到达到期时间而未取得显式决议即 fail；
  无到期者用带理由的 `unassigned:<理由>` 并表示不得跨过 `reviewByMilestone` 收口。
- 复审触发点：任一次轮次上限到达、任一登记项到期、以及 `reviewByMilestone` 声明的
  里程碑收口（当前为 M2，届时所有 `unassigned:<理由>` 项必须转期或关闭）；复审由
  产品负责人主持。
