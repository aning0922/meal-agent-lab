# 09P：owner 决策请求（一页）

- **给谁看**：产品负责人——以下七项由您一人裁定，别人无权代答。
- **为什么现在**：09P 首个 release 的关键路径不在代码上。以下七项多数一旦不答，工作
  **无法推进**（默认就是停）。本页可独立阅读，**无需先读任何其它文件**。
- **怎么用**：每条在「答复」行写 `同意 / 不同意 / 改范围`；拿不准写 `暂缓` 并一句说明。

---

**决定 1　是否授权把 09P 治理落到 `main`，或至少推到 `origin`？**
今天 09P 的七条分支只在本地、从不推送，过程目录 `.local/` 又被 git 排除——单机丢失即全失。
落 `main`/推 `origin` 后，索引事实源才与治理规则一致，单点故障风险才解除。
**不答复的默认**：维持现状——治理只存在于本机未推送分支，单点故障持续。
答复：同意 / 不同意 / 改范围（只推 `origin` 不落 `main`？）

**决定 2　是否授权修复三处审计工装缺陷，并签发一份全新命名的 M1 动态审计？**
M1 的三个旧 BLOCK（r1/r2/r3）是**工装自伤**，不是已确证的运行时缺陷。新审计
**不叫 B-r4、不是重试、不解封旧 BLOCK**；且 B CLEAN **不等于** M1 Accepted。
**不答复的默认**：审计无法运行，M-2 不闭合，M-4 被 M-2 卡住。
答复：同意（执行者：____；范围签发方式：____）/ 不同意 / 改范围

**决定 3　是否授权 ADR-0009 §8 第 2 项的有界合成纵切？范围、精确 SHA、交付边界如何钉死？是否以该合成范围取代入口评估对 contracts/API/DB/client/migration 的禁令？**
仅合成数据、仅本地 E2E。这是约 31 项证据义务的**唯一共享解锁点**。三项强制更正：
引擎读**未脱敏**约束、菜谱**只经 `foodConceptId`** join 库存、快照用四段 digest 或显式登记为延迟。
**不答复的默认**：M-4 不开始，约 31 项证据义务失去唯一解锁点——按停止条件**重新规划**。
答复：同意 / 不同意（则重新规划，不默认前进）/ 改范围 + 钉死的 SHA 与边界

**决定 4　十二个角色里，哪些由现有工程/产品角色内部填实、哪些必须外部购买？外部预算与可得性？**
内部七个（六个 Steward/Owner 加产品负责人 `product_owner`）可由现有角色兼任；外部食品安全
审核人、法律/合规、文化/伦理审核人须外部委任（闭集见冻结的 M1 就绪契约
`stage09p-m1-minimal-deterministic-readiness-contract-r4` §3.3）。角色名本身不构成审核证据。
**不答复的默认**：外部委任无法开始，M1 Accepted 永不到来，首个 release 必须正式缩窄。
答复：同意 / 不同意 / 改范围（预算上限：____；可得窗口：____）

**决定 5　Safety Approver 是否也必须为外部方（独立于项目实施者与内容生产者）？Recipe QA 是否外部？**
就绪契约要求每人恰好一项**独立、无利益冲突**的权限（§3.3 的 `independent`/`disclosedConflicts`），
且 r4 §5.3 已强制十二角色有效自然人身份**两两互异**——Safety Approver 与外部食品安全审核人
必为不同自然人这点已被契约裁定；仍未关闭的是其**组织/利益独立性**（是否来自项目外部）。
**不答复的默认**：Safety Approver 的外部归属不确定，M-3 外部方名单不完整。
答复：同意（最保守：Safety Approver 外部 + Recipe QA 外部）/ 不同意 / 改范围

**决定 6　首个 release 是否正式缩窄为「经外审的 allergen 词表 + 绑定 + 约十二道双人复核菜谱 + 高风险安全规则族」，其余数据类不激活？**
不缩窄就等于宣称完整 MVP 内容广度，而完整广度没有外部审查路径。缩窄后，未激活类的家庭
硬规则**诚实地阻断**，不编造。
**不答复的默认**：范围维持完整 MVP 广度，首个 release 无从定义，也无 active 数据发布。
答复：同意 / 不同意 / 改范围
