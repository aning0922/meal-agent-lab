# Meal Agent 低保真原型

- 版本：0.4
- 状态：Accepted for technical validation
- 更新时间：2026-07-23
- 原型入口：`apps/meal-agent-prototype/`

## 1. 原型范围

本轮原型只验证 P0 核心闭环，不代表正式视觉方案，也不绑定后续客户端技术栈。

```text
登录与恢复 → 首次引导 → 首批食材 → 今天吃什么 → 建议组合与可选菜
          → 共享采购 → 开始做饭 → 完成与库存确认 → 完成回执
```

库存临期、搜索与批次历史、“我的”、成员邀请与隐私、Agent 二级页均与主闭环相连。桌面评审面板可在每个页面模拟 11 类状态，正式定义见 [P0 页面状态基线](p0-page-state-baseline.md)。

### 已决定

- 首发场景按微信小程序的单手、窄屏体验设计。
- 首次使用只要求填写硬约束；普通偏好、精确数量和日期均可跳过。
- 系统先建议本餐做几道菜并预选一组可执行组合，再提供可选菜供用户增减；整餐时间、采购项和库存覆盖随选择实时重算。
- 采购的“已买”和库存的“已入库”保持为两个状态。
- 完成状态与库存扣减合并为同页渐进披露；用户确认具体批次、实际用量和剩菜回库后才写入变更。
- 第四个一级导航使用“我的”，家庭成员、权限、邀请和隐私作为二级内容。

### 仅为原型假设

- 示例家庭、成员、库存、菜谱、日期和数量均为虚构演示数据。
- 原型用单机状态模拟多人同步、库存版本检查和写入结果，不连接真实服务。
- 成功阈值仅用于本轮可用性测试，验证后再决定是否纳入产品指标。

## 2. 页面清单

| 编号 | 页面 | 核心任务 | 关键交互 |
| --- | --- | --- | --- |
| A-01 | 登录与恢复 | 区分新用户、邀请加入和已有家庭恢复 | 快捷登录；新设备恢复；邀请状态与权限校验 |
| O-01 | 首次欢迎 | 理解最短价值路径 | 创建家庭；说明不必盘点整个冰箱 |
| O-02 | 用餐成员与硬约束 | 建立真实用餐者和不可绕过的限制 | 添加档案；确认过敏/禁忌；普通偏好可跳过 |
| O-03 | 厨艺与厨具 | 过滤不可执行菜谱 | 选择厨艺；勾选已有设备 |
| O-04 | 常备调味品 | 用模板快速建立基础库存 | 一键选择常用组合；未知项不默认为没有 |
| O-05 | 首批食材 | 添加 5–10 个确定存在或想先消耗的食材 | 最近/常用快捷选择；模糊数量；连续添加；统一确认 |
| H-01 | 今天 | 发起一餐并看到需优先处理事项 | 临期摘要；本餐参与者；“今天吃什么”；快捷 Agent 输入 |
| I-01 | 库存与临期 | 区分可优先使用、日期未知和高风险未知批次 | 日期来源；安全阻断；用它找菜单；库存 Agent |
| I-02 | 库存搜索与筛选 | 快速找到聚合食材并保留未知状态 | 搜索；位置/日期/需处理筛选；无结果恢复 |
| I-03 | 批次详情与历史 | 核对批次来源并执行可追溯操作 | 日期来源；置信度；快捷确认单；事件历史与纠正 |
| R-01 | 本餐条件 | 用最少操作确认推荐条件 | 参与者、厨师、时间、采购容忍度；永久约束与本次偏好分区 |
| R-02 | 建议组合与可选菜 | 理解建议数量并快速组成今晚的一餐 | 查看预选菜和推荐理由；增减可选菜；实时查看整餐时间、采购项和库存覆盖 |
| R-03 | 本餐组合详情 | 判断整餐是否可执行并创建本餐计划 | 查看份量、食材、步骤、安全提示；确认前再次校验 |
| S-01 | 共享采购 | 在购物现场共同勾选缺少项 | 合并同类项；保留来源；显示最后操作者；已买进入待入库 |
| S-02 | 已买待入库 | 回家后批量补齐必要库存信息 | 模糊数量、位置和日期来源；确认后创建新批次 |
| M-01 | 我的 | 区分个人资料与家庭共享设置 | 当前账号；家庭成员；硬约束；厨艺厨具；隐私入口 |
| M-02 | 成员、邀请与隐私 | 管理成员身份与个人数据控制 | 登录邀请/用餐档案；最少披露；导出、退出和删除路径 |
| AG-01 | Agent 二级页 | 带着来源页对象完成解释或候选修改 | 工具结果；未知信息；待确认变更；同一操作纠错 |
| C-01 | 开始前检查 | 在开火前确认可做和安全要求 | 人数、设备、准备事项、现有/缺少食材、最新库存校验 |
| C-02 | 做饭模式 | 按步骤执行并能暂停恢复 | 当前步骤、用量、火候、安全点和进度 |
| C-03 | 完成与库存确认 | 在一个页面确认完成状态和实际消耗 | 全部/部分/没做；具体批次；调整/排除；冲突重算；剩菜回库 |
| C-04 | 完成回执 | 确认闭环已完成并给出轻量反馈 | 消耗事件摘要、剩菜批次、口味/难度/时间反馈 |

每页还需要通过评审面板检查首次空状态、加载、未知、失败、无权限、部分成功、并发冲突、安全阻断、重复提交和中途恢复。

## 3. 本轮验证目标

### A. 录入成本

**待验证问题**

1. 用户能否理解“不必完整盘点”，只录入最确定的 5–10 项？
2. 模板、最近项和模糊数量能否明显减少逐项输入？
3. “跳过/未知”是否会被误解为“家里没有”？
4. 硬约束的确认是否足够郑重，但没有让普通偏好拖慢首次使用？

**原型成功信号（待验证阈值）**

- 用户在 2 分钟内完成一个家庭、两位用餐者、厨艺厨具、调味品和 5 项食材。
- 首批食材阶段不要求输入精确重量或日期也能继续。
- 用户能准确说明至少一项“未知信息”不会被系统当成“没有”。

### B. 组合选择效率

**待验证问题**

1. 用户能否理解系统为什么建议做 2 道，以及预选组合的餐桌结构？
2. 用户能否快速增减可选菜，并理解单道菜带来的时间、采购和库存影响？
3. 整餐总时间、缺少项、库存覆盖和关键假设是否会随选择清楚更新？

**原型成功信号（待验证阈值）**

- 用户在 20 秒内确认 2–3 道菜，并能说明为何保留或加入其中一道。
- 用户不进入详情页，也能回答“加这道菜会多花多久、多买什么”。
- 用户在确认前能发现整餐缺少项和一条动态估算假设。

### C. 餐后扣减流程

**待验证问题**

1. 用户是否理解选择完成状态后仍需在同页最终确认库存写入？
2. 预计消耗按具体批次展示是否清楚，调整和排除是否容易发现？
3. “只做了一部分”“库存被他人修改”“剩菜回库”是否能在一个短流程中处理？
4. 完成回执能否让用户确信扣减和回库都已记录？

**原型成功信号（待验证阈值）**

- 用户在 45 秒内完成状态选择、批次核对、一次用量调整和剩菜回库。
- 用户在最终确认前能说出会扣减哪些批次，并知道可以取消某一项。
- 并发变化时，用户能理解系统会按最新库存重算且不会产生负库存。

## 4. 建议评审任务

1. **低成本首次使用：** 从 A-01 开始，完成登录/创建家庭，不填写任何精确重量或日期，完成 5 项食材录入并进入 H-01。
2. **组合快速选择：** 从 R-01 开始，用“3 人、30 分钟、少买菜”的条件查看系统建议，增减一道可选菜后确认本餐，并说明选择理由。
3. **共享采购：** 从 S-01 开始，勾选鸡蛋为已买，观察家庭同步信息，并完成待入库确认。
4. **部分完成与纠正：** 在 C-03 同页选择“部分完成”，把鸡蛋消耗从 3 个改为 2 个，排除未使用的葱，并保存一盒剩菜。
5. **并发冲突：** 在 C-03 触发“库存刚被家人更新”的演示，确认用户能找到重算后的批次与待盘点项。
6. **临期与安全阻断：** 从 I-01 分别处理标签日期明确的番茄、日期未知的鸡蛋和冷链未知的生鸡肉。
7. **页面状态：** 在任意页面依次切换失败、无权限、部分成功、安全阻断、重复提交和恢复，复述哪些内容已经写入。
8. **P0 辅助页面：** 完成新设备恢复、库存搜索和批次纠正，生成成员邀请与数据导出待确认任务，并从业务页进入 AG-01 后返回来源页。

## 5. 评审记录建议

每个任务记录完成时间、误触次数、是否求助、口头理解与放弃原因。优先记录以下语言信号：

- “为什么现在就要填这个？”
- “为什么建议做这几道？”
- “加这道菜会多买什么、多久？”
- “完成和扣库存放在一页后，还需要多少操作？”
- “买了以后为什么还没进库存？”
- “这个数量不准怎么办？”

评审后把结论分为“保留”“需要调整”“重新打开产品决策”，并同步更新 `docs/product/open-decisions.md` 和 `docs/project-status.md`。
