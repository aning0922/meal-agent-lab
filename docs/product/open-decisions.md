# 产品开放决策

- 版本：0.1
- 状态：Accepted for prototyping
- 更新时间：2026-07-23

产品负责人已于 2026-07-23 确认采用下表方案，作为低保真原型和后续技术验证的产品基线。原型验证发现明显问题时，通过文档变更记录重新打开对应决策。

| 编号 | 问题 | 已确认决策 | 影响 |
| --- | --- | --- | --- |
| PD-001 | 首发载体 | 微信小程序优先，架构保留 App 扩展 | 影响登录、通知、分享、离线和技术栈 |
| PD-002 | P0 录入方式 | 手动搜索、最近、常用模板和批量添加；语音/OCR 放 P1 | 控制 MVP 风险，先验证用户是否愿意维护库存 |
| PD-003 | 菜单颗粒度 | 支持单道主食或 1–3 道菜的一餐组合，不做多日计划 | 影响菜谱结构、份量和做饭流程 |
| PD-004 | 首批菜谱规模 | 100–300 道经过审核的常见家常菜 | 影响内容准备和推荐覆盖率 |
| PD-005 | 数量模型 | 模糊数量优先，精确数量可选；保留用户原始表达 | 降低维护负担并避免伪精确 |
| PD-006 | 家庭角色 | 所有者、普通成员、无登录用餐档案 | 避免 MVP 权限模型过重 |
| PD-007 | 提醒范围 | P0 只做应用内提醒，外部通知放 P1 | 降低平台权限和通知噪音风险 |
| PD-008 | 营养能力 | MVP 只做一般食物多样性标签，不做热量或医疗营养承诺 | 降低数据和安全风险 |
| PD-009 | 购物协作 | P0 做共享勾选与买后入库，不做分派、比价和下单 | 保留闭环，控制外部集成成本 |
| PD-010 | Agent 入口 | 首页快捷输入 + 各业务页上下文入口，不设独立底部 Tab | 保持任务导向，避免产品退化成聊天框 |
| PD-011 | 首发多家庭 | 数据模型支持，界面允许切换；普通用户默认一个家庭 | 支持未来照顾父母等场景而不过度暴露复杂度 |
| PD-012 | 商业化 | MVP 不植入导购或付费墙，先验证留存和完成餐次 | 避免商业目标影响推荐可信度 |
| PD-013 | 第四个一级导航名称 | 暂用“家庭”，同时包含“我的资料”；原型阶段与“我的”方案对比 | 影响用户对共享设置与个人设置的理解 |
| PD-014 | 菜单选择交互 | 系统先建议 1–3 道菜并预选可执行组合，再提供可选菜供用户增减；不要求在三个完整菜单之间三选一 | 降低整餐选择的抽象程度，并让份量、采购与耗时随组合变化可见 |

## 执行顺序

1. 制作覆盖首次录入、菜单选择、采购和扣减流程的低保真原型。
2. 用目标用户视角验证维护成本、组合选择和餐后扣减三个高风险交互。
3. 以微信小程序为首发目标执行跨平台技术验证，同时保留 App 扩展边界。
4. 在准备正式菜谱和保质期数据前，单独确认来源、许可和审核责任。
